1. 执行结论

推荐组合：Spark 的 DomainJoin 外壳 + Calcite 的 2025 状态模型 + DuckDB 的终局语义与共享执行

Doris 不应继续把能力堆在若干局部 Apply → Join pattern 上，也不应先完整复刻 2015 bottom-up。正确方向是先建立一个独立的、全计划范围的 holistic unnesting phase；第一阶段仅覆盖现有可分析的基础计划形态，但数据结构和 traversal contract 从一开始就对齐 2025。

01 Spark：第一版模板

显式 DomainJoin 占位符、递归 rewrite 返回三元状态、最终用普通 Aggregate + Join 物化 D。与 Doris 同为 JVM 和分布式 SQL，工程距离最近。

02 Calcite：终局状态模板

TopDownGeneralDecorrelator 直接对应 2025：全局相关定义、去重自由变量节点、每个子树的输出映射、嵌套 Correlate 合并。Java 表达最清楚，但仍是实验性组件。

03 DuckDB：正确性终局

覆盖面、NULL/COUNT/Max1/MARK 语义以及 D 的共享执行最成熟；当前实现已走 holistic 路线。适合作为行为 oracle，不适合第一版逐行翻译。

2. 为什么终局必须以 2025 为架构基线

2015 bottom-up 每次只消除一个 dependent join。深层嵌套时，不同层独立形成 D，后续可能在不真实存在的绑定笛卡尔积上执行聚合；结果仍可能正确，但中间规模会爆炸。2025 的变化不是增加几条规则，而是改变处理顺序和状态所有权。

完整代数化保留全部 dependent joins
预标注producer / access / LCA
Top-down 消除祖先与后代一起处理
Domain loweringD 或 substitution
常规优化join reorder / CBO / physical

关键 invariant

不同 unnesting state 的 D 不跨越嵌套 dependent join 盲目下推。遇到后代 Apply 时，要么在祖先 pass 内合并处理，要么明确停止并让后代在后续 top-down 顺序中处理。

4. Spark：DomainJoin 驱动的递归 rewrite

Spark 的核心不是 Catalyst 中一串彼此独立的 pattern rule，而是 DecorrelateInnerQuery 这个带状态递归过程。它返回新的 inner plan、和 outer 的 join conditions、以及 outer reference 到 inner/domain attribute 的映射；后续再按 scalar、lateral、EXISTS/IN 做 lowering。

核心 pattern / action

PatternAction停止 / 约束
子树无 OuterRef，待绑定集为空原样返回正常终止
子树无 OuterRef，待绑定集非空插入 DomainJoin(DAttrs, child)；建立 DAttr <=> OuterRef 和 replacement map之后统一 lowering
Filter(correlated AND local)无聚合屏障时上提相关谓词；收集安全等值 substitution；残余 OuterRef 改写成 DAttr聚合下仅一对一等值可上提
Project改写表达式；把上层 join conditions 需要的属性及 domain hidden slots 透传必须保持 ExprId 映射
Aggregate以 aggregated 状态递归；把 binding attrs 加入 group-by 与 output；静态聚合处理空输入COUNT default / count bug 单独修正
Window把 binding attrs 加入 partition 与输出Window 自身 OuterRef 仍受限制
Limit / Offset / Sort改写为按 domain attrs 分区的 ROW_NUMBER + 范围过滤保证每个 binding 单独限行
Join按 join type / preserved side 选择传播侧；必要时两侧携带 D 并用 null-safe key 对齐ON 条件与 unmatched-row 语义决定分支
SetOp / Distinct完整 D 进入所有 branch；统一 domain slot 位置；按 binding 隔离去重child schema / ExprId 必须对齐
未覆盖多子节点fail fast不保留可执行 Apply fallback

对 Doris 的主要价值

第一版可以直接采用 Spark 的“placeholder 后统一 lowering”边界：先解决正确的逻辑计划，不要求增加物理 DelimJoin；同时 rewrite API 从第一天就返回 plan 之外的映射状态，避免继续把状态塞进零散 Rule。

不要把 Spark 原样当作 2025 终局

Spark 当前仍是 2015 DomainJoin 框架的广覆盖实现：过程较集中，Analyzer 保留 correlation-path 白名单，outer plan 在 D lowering 中会逻辑复制，COUNT 也存在两条修正路径。它最适合提供 transfer function 和回归矩阵，而不是直接决定 Doris 的最终状态组织。

5. DuckDB：holistic rewrite + 可共享的 Delim domain

DuckDB 的旧路线是在规划每个相关子查询时立即局部 flatten。2025 重构后，先把整条语句构造成含 LogicalDependentJoin 的完整逻辑计划，再从外向内统一消除；当前主干继续强化了 binding replacement graph、subtree access cache 和复杂 join/CTE 规则。

核心 pattern / action

PatternAction关键状态
DependentJoin(L,R,C)从 L 定义去重 C 域；D 经 DelimGet 进入 R；outer refs→D bindings；以 L.C IS NOT DISTINCT FROM D.C 接回bindings、replacement graph、parent、join type、NULL propagation
R 子树不再访问 C停止下推，形成 R × DelimGet(D)正常停止点，不是失败
Filter / Project递归、改写 outer refs、保护 D keys 输出binding layout 必须稳定
Aggregate / Distinct / WindowD keys 分别加入 group、distinct target、window partition；静态 aggregate 用外连接恢复缺组COUNT NULL→0
Cross / Join一侧相关只推一侧；两侧相关分别携带 D 并补 null-safe equality；outer join 选 preserved-side representative每个子树的 domain access cache

物理复用给 Doris 的启示

专用 Delim 执行

LHS batch 一次输入，同时送往原始 L 路径和 HashDistinct 路径；多个 DelimScan 共享 D。这避免了复制一棵昂贵 outer plan。

Materialized CTE lowering

调研快照中 delim_join_as_cte 已默认开启：DelimJoin/DelimGet 被降成两个共享 CTE 层，先物化完整 L，再从其 consumer 计算 D。Doris 已有 CTE producer/consumer，可把它作为专用物理算子之前的工程过渡。

不要从旧 offset-based 代码移植

Doris 应直接使用 ExprId/Slot replacement graph 与显式 output contract，避免复制 DuckDB 旧实现中依靠位置、offset 和 table index 算术传递状态的方式。

6. Calcite：传统 Frame decorrelator 与 2025 top-down 实验实现

传统 RelDecorrelator 以每个 RelNode 的 Frame 和输出位置映射逐层传播相关列，适合观察成熟 Calcite 如何维护字段位置、COUNT 和 scalar 规则，但它不是 Doris 的终局模板。新的 TopDownGeneralDecorrelator 明确基于 2025 论文，并把 D 与父子 unnesting state 提升为一等对象。

TopDownGeneralDecorrelator 的状态

对象职责对 Doris 的映射
CorDef相关变量的 owner correlation id + field index不能继续只用裸 Slot；需要 owner/depth
hasCorrelatedExpressions预先标注每个 RelNode 子树是否仍有当前相关访问PlanTopologyIndex / access summary

主要 pattern / action

Correlate
先登记 left required columns 为 CorDef，构造/更新 D；递归 unnest RHS；最终增加 L IS NOT DISTINCT FROM D 并转 Join。
Filter / Project
记录等价关系、改写 outer references、追加相关列输出并维护 old-to-new output map。
Aggregate
把相关代表列加入 group/output；对 static aggregate 先做 value-generator / left join，确保每个 binding 都有结果。
Join / SetOp
按访问分布拆分状态；多 branch 输出统一 CorDef layout；join type 决定 representative 与 nullability。
Sort / Limit
按相关列 partition 的 ROW_NUMBER 重写 per-binding order/offset/fetch。
Stop
访问列表/相关检测为空时，在“安全 substitution”与“加入 D”之间选择；不把两个独立 D 穿过嵌套 Correlate。

成熟度边界

TopDownGeneralDecorrelator 仍标记为 experimental，默认关闭；当前主干已通过连接属性、Programs.subQuery 和 DecorrelateProgram 进入 opt-in 全链路，Javadoc 中“not yet integrated”已经部分过时。它适合做 Doris 设计参照和测试 oracle，但仍不能视为默认生产路径。

DAG 与 annotation cache

同一个共享 RelNode 在不同相关上下文中可能得到不同的自由变量集合。Calcite 预处理使用 noDag=true 规避污染；Doris 更适合让缓存键包含 (plan identity, correlation-context fingerprint)，为后续 CTE DAG 保留正确扩展方向。

最大的架构风险

直接修改 ScalarApplyToJoin，遇到非 EQ 就现场拼一个 D，只能修单层 Aggregate(Filter(scan))。它不会解决访问标注、嵌套 Apply、两侧 Join、输出 remap 和 D 共享，之后很可能推倒重来。

8. 建议的 Doris 终局架构

保持 LogicalApply 作为 SQL lowering 后的 dependent-join IR，但把消除过程从 rule list 升级为一个独立 topic。第一版即采用以下 phase 边界，未支持的复杂 operator 仍可 fail fast；以后只增加 operator handler，不改变总流程。

8.1 预处理：PlanTopologyIndex

先用一次只读 DFS 建立临时索引，不要求立刻改造 Nereids 全局 Plan ID：

PlanTopologyIndex
  parentByIdentity      Plan → parent edge(s)
  depth / tin / tout    LCA 与 subtree containment
  producerByExprId      ExprId → producing Plan
  accessesByPlan        Plan → outer refs used locally
  dependentJoinInfo     Apply → {outerRefs, accessSites, parentApply}
  subtreeAccessSummary  (Plan, Apply) → correlated / volatile / none

第一版计划仍是树，可使用 IdentityHashMap 与 Euler interval。以后处理 CTE DAG 时把 parent 改为多边并切成共享子树，不应在第一版预先实现完整 indexed algebra。

8.2 核心 rewrite API

RewriteResult unnest(
    Plan node,
    UnnestingContext ctx,
    Set<AccessSite> remainingAccesses)

UnnestingContext
  info: {apply, outerRefs, DomainSpec, parent}
  cclasses: scoped equivalence classes
  repr: BindingReplacementGraph
  outputMap: old ExprId → new Slot
  semantics: join type / null / multiplicity flags

RewriteResult 不能只返回 Plan。Project、Aggregate、SetOp 与 Join 都会改变 output layout，父节点必须收到 binding outputs 和 old-to-new mapping；这一点 Spark、DuckDB、Calcite 三者虽然命名不同，但结论一致。

整个 pass 应当事务式构造候选树：遇到尚未支持的节点时丢弃候选并回到现有 Doris 路径；只有成功完成并通过 invariant 检查后才替换原计划。若旧路径同样无法处理，再统一报告 unsupported，不能留下半改写计划。

8.3 DomainSpec 先懒描述、后统一 lowering

DomainSpec
  source       := Apply.left 的真实逻辑结果
  keys         := outerRefs
  aliases      := fresh ExprIds used inside RHS
  materialize  := AUTO | DUPLICATE_TREE | SHARED_CTE | PHYSICAL_DELIM

D := DISTINCT Project(keys, source)

holistic pass 内只插入 LogicalDomainJoin 或等价 placeholder；结束后统一降低为普通 Aggregate + Join。这样逻辑正确性与执行共享解耦：第一版可复制 outer tree，第二版使用 CTE producer/consumer，最终再考虑专用 physical delim fan-out。

8.4 决策接口

if safeEquivalentRepresentativeExists(outerRef, cclasses, subtreeOutput):
    repr[outerRef] := chosen inner slot        // substitution
else:
    repr[outerRef] := DomainSpec.alias         // explicit D

第一版策略应确定性且保守：只在明确的一对一等值与可见 Slot 上 substitution，其余一律 D。之后再让 CBO 根据 D 的选择性、distinct cardinality、已有 key/FD 和分布属性选择。

9. Doris 核心 operator 的 pattern / action contract

为何第一版仍能覆盖论文 Q2

Q2 的 RHS 是 global Aggregate → Filter → Scan。Filter 中的 OR 不需要拆成等值 conjunct；整个表达式只需把 s.id / s.major / s.year 改写成 D aliases。Aggregate 再按三个 aliases 分组，最后 null-safe join-back 即可。

10. 分阶段落地路线

Phase 0
基础设施，不改行为
PlanTopologyIndex、OuterRefKey、DependentJoinInfo、RewriteResult、BindingReplacementGraph、DomainSpec。 在现有成功/失败用例上仅输出 debug annotation；建立“所有 access 都归属唯一 Apply”的 invariant。
Phase 1
显式 D vertical slice
支持 Scalar Apply → [Project] → Global Aggregate → [Project] → Filter → 单输入子树。等值沿用现有快路径，非等值/OR 走 D；先支持 MIN/MAX/SUM/AVG。目标是论文 Q2 与 Doris 当前非 EQ 回归测试由 error 变为正确结果。
Phase 2
holistic nested Apply
切换 top-to-bottom 调度；实现 parent context 与访问标注；祖先 pass 遇到后代 Apply 时合并处理，消除独立 D 笛卡尔积。加入 2025 crash.sql 形态的规模测试。
Phase 3
核心语义补齐
COUNT/empty-input、Max1/LeftSingle、Window、inner/left/right/full Join、SetOp、Mark/Semi/Anti。此阶段完成“普通 SQL 计划树”上的广覆盖。
Phase 4
复杂结构
ORDER BY LIMIT per binding、共享 CTE DAG、recursive CTE、full-join condition subquery；将 Analyzer 的提前拒绝逐项后移到 holistic pass。
Phase 5
业界最佳执行
D 的 CBO 位置选择、FD/unique-key substitution、CTE/spool 共享、分布式 distinct 与 exchange property、可选 physical delim fan-out、holistic CE 与 join-order integration。

建议的代码边界

rules/rewrite/subquery/
  HolisticApplyEliminator.java        // orchestration + top-down traversal
  CorrelationPlanIndex.java           // preprocessing annotations
  UnnestingContext.java               // outerRefs / D / parent / cclasses / repr
  UnnestingRewriteResult.java         // plan + binding outputs + output remap
  DomainSpec.java                     // lazy domain description
  DomainLowering.java                 // Aggregate+Join / CTE lowering
  OperatorUnnestingRules.java         // pattern/action handlers
  UnnestingValidator.java             // no Apply / no outer ref / invariants

这是概念边界，不要求第一批 PR 一次创建全部类。重要的是把 orchestration、state、operator handlers、domain lowering 和 validation 分开，避免重新形成一个巨型 Rule。

11. 验证矩阵与不变量

每次 rewrite 后必须成立

  • 任何 outer reference 都能唯一定位到提供它的 dependent join；不能靠同名 Slot 猜测。
  • 每个 repr(c) 必须真实存在于当前子树输出；Project/SetOp 后必须更新 output map。
  • D 的 key 采用集合语义去重，NULL 绑定参与分组，并用 NullSafeEqual join-back。
  • Aggregate / Window / Distinct / Limit 的语义必须按 binding 隔离。
  • 最终进入常规优化前：无 LogicalApply、无 outer refs、无 domain placeholder。
  • 规则无法证明正确时 fail fast，不保留不可执行的 dependent plan。

补充边界

Materialize 的“distinct outer bindings + join-back”与 2015 方案几乎相同，但当前仓库使用 Business Source License 1.1；可读设计，不建议向 Apache Doris 复制实现。CockroachDB、Trino、DataFusion 等存在 decorrelation 规则，但本报告未把它们认定为完整显式 D / 2025 holistic 实现。

结论：先提交无行为变化的 unnesting foundation，再以论文 Q2 做显式 D vertical slice；不要把最终架构绑死在单层 ScalarApply pattern 上。
