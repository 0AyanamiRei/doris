不从类清单开始，而是固定一条三表 SQL，跟着它依次变成未绑定逻辑树、已分析逻辑树、 重写后的逻辑树、Memo 中的候选图、获胜的 PhysicalPlan，以及最终的 fragments、exchanges 和 worker instances。每一层都回答四件事：入口在哪里、对象变了什么、源码怎样继续、下一层拿到什么。

先把“处理阶段”和“观察视图”分开

一次普通查询的核心对象只沿下面的主链迁移。EXPLAIN 在不同边界提前返回或选择不同打印器， 因而让我们看到各层状态。本文不介绍 LOGICAL PLAN PROCESS、Nereids trace 或 DPHyp trace 等日志型输出。

  1. SQL / ExplainCommandparser 先得到命令 AST，再把内部 query plan 交给 NereidsPlanner。
  2. Parsed LogicalPlanUnboundRelation、UnboundSlot、SQL 原始 join 骨架。
  3. Analyzed LogicalPlanrelation、slot、类型、ExprId 与语义约束已经绑定。
  4. Rewritten LogicalPlan谓词下推、列裁剪、join 归一化后，成为 CBO 输入。
  5. Memo DAGGroup 保存等价结果，GroupExpression 保存候选关系表达式。
  6. Chosen PhysicalPlan按 required property 递归取出最低成本物理树，再做 post-process。
  7. Shape / Physical views同一棵 PhysicalPlan 的紧凑视图和详细视图。
  8. DistributedPlan graphPhysicalDistribute 翻译成 Exchange/fragment，再分配 worker instances。
最重要的源码事实： NereidsPlanner#getExplainString 对 SHAPE 调用 optimizedPlan.shape("")，对 PHYSICAL 返回 cost + optimizedPlan.treeString()。它们共享同一个 optimizedPlan 字段。
SQL 写法 内部 ExplainLevel 观察对象 该命令在哪里截断 / 打印
PARSED PLAN PARSED_PLAN parsedPlan.treeString() 在 preprocess、锁表和 Analyzer 之前直接返回。
ANALYZED PLAN ANALYZED_PLAN analyzedPlan.treeString() Analyzer 完成后、whole-tree Rewriter 之前返回。

The single running example

全文只跟这一条三表 SQL

查询使用 TPC-H 的 customer、orders、lineitem， 但刻意去掉聚合与 LIMIT，只保留三表连接、三个单表过滤、四列投影和 ORDER BY。 这样每次树变化都能在十五行左右的逻辑输出中看清。 

SELECT
    c.c_custkey,
    o.o_orderkey,
    l.l_linenumber,
    o.o_orderdate
FROM customer c
JOIN orders o
  ON c.c_custkey = o.o_custkey
JOIN lineitem l
  ON o.o_orderkey = l.l_orderkey
WHERE c.c_mktsegment = 'BUILDING'
  AND o.o_orderdate < DATE '1995-03-15'
  AND l.l_shipdate > DATE '1995-03-15'
ORDER BY o.o_orderdate, o.o_orderkey, l.l_linenumber;

主线采用普通 Cascades

配套目录同时保存 Cascades 与显式 DPHyp 结果；本文固定使用 cascades.txt，即 enable_dphyp_optimizer=false。 DPHyp 会改变 join-order 分支，但不会改变 parser → analyzer → rewrite → physical copy-out → distribute 这条外层流水线。

不要固定易变 ID

文中的 PlanId、ExprId、GroupId、tablet/instance ID 和 cost 只用于解释本次快照。 稳定事实是对象类型、调用关系、property 语义和数据流，不是某个具体编号。

先分清命令 AST 和被解释的查询树，后面才不会把 ExplainCommand 当成优化器输入。

入口ConnectProcessor.executeQuery
命令对象ExplainCommand
被解释对象内部 LogicalPlan

ConnectProcessor.executeQuery
└─ parseWithFallback
   └─ NereidsParser.parseSQL
      └─ LogicalPlanBuilder.withExplain

StmtExecutor.executeByNereids

PARSED PLAN：SQL 先变成未绑定逻辑树

这一层确认语法结构，不做 catalog 绑定，也不判断 join 算法、分布方式或成本。

主构造器LogicalPlanBuilder

本 SQL 的 parsed tree

UnboundResultSink
└─ LogicalSort('o_orderdate, 'o_orderkey, 'l_linenumber)
   └─ LogicalProject('c_custkey, 'o_orderkey, ...)
      └─ LogicalFilter(三个 WHERE 谓词仍在一个 AND 中)
         └─ LogicalJoin(other=[o_orderkey = l_orderkey])
            ├─ LogicalJoin(other=[c_custkey = o_custkey])
            │  ├─ LogicalSubQueryAlias(c)
            │  │  └─ LogicalCheckPolicy
            │  │     └─ UnboundRelation(customer)
            │  └─ LogicalSubQueryAlias(o)

此时已经确定

  • FROM 中有三张关系，join 语法是左深树。
  • ON、WHERE、SELECT、ORDER BY 的表达式骨架完整。
  • 表别名作用域已经用 wrapper 表示。

此时仍未确定

  • 表属于哪个 catalog/database，列引用是否合法。
  • slot 的类型、nullable、ExprId 与真实来源。
  • 等值条件能否进入 hashJoinConjuncts。
  • join order、Hash/NLJ、broadcast/shuffle 与 cost。
LogicalSubQueryAlias 不代表 SQL 子查询： 普通的 customer c 也会经过 visitTableName → UnboundRelation → withCheckPolicy → withTableAlias， 最后由 LogicalSubQueryAlias 承担关系别名作用域。

当 ExplainLevel 是 PARSED_PLAN 时， NereidsPlanner#planWithLock 在 preprocess()、 initCascadesContext()、collect/lock table 与 Analyzer 之前直接返回。

交给下一阶段的对象： 一棵语法正确但仍含 UnboundRelation、UnboundSlot 的 LogicalPlan。Analyzer 的任务是让这棵树获得可验证的数据库语义。

ANALYZED PLAN：把名字绑定成有类型、有身份的对象

Analyzer 解决“这条 SQL 到底在说什么”，而不是“怎样执行最便宜”。

输入Unbound LogicalPlan
工作区CascadesContext.rewritePlan
执行器Analyzer batch jobs
输出Bound LogicalPlan
NereidsPlanner.planWithLock
├─ preprocess(plan)
├─ initCascadesContext(plan, requiredProperties)
├─ collectAndLockTable(...)
└─ planWithoutLock
   └─ analyze(...)
      └─ CascadesContext.newAnalyzer().analyze()
         └─ Analyzer.execute()
            └─ AbstractBatchJobExecutor.execute()
               └─ ANALYZE_JOBS

对本 SQL 最关键的一组 bottom-up rules

BindRelation 从 StatementContext/catalog 中取得真实表，把三个 UnboundRelation 变成 LogicalOlapScan。
CheckPolicy 应用行级策略与数据掩码；本实验环境没有额外策略，所以 LogicalCheckPolicy wrapper 被消去。
BindExpression 把 join/filter/project/sort/sink 中的未绑定表达式解析到 relation outputs，并完成函数与类型解析。

本例表列 Slot 的 ExprId 在 LogicalCatalogRelation#computeOutput 构造 catalog relation 输出时分配；BindExpression 复用这些带 ExprId 的 outputs 去解析上层表达式。

└─ LogicalSort(o_orderdate#12, o_orderkey#8, l_linenumber#20)

      └─ LogicalFilter(三个已绑定谓词)

观察点 PARSED ANALYZED 为什么重要
relation UnboundRelation(customer) LogicalOlapScan(internal.db.customer) 已经拿到真实 schema、table/index 元数据。
slot 'o.o_orderkey o_orderkey#8 同名列可以靠 ExprId 精确区分，类型与 nullable 已知。
sink UnboundResultSink LogicalResultSink 最终输出表达式已经绑定。
join / filter 未绑定表达式 已绑定，但仍保留原始集中位置 Analyzer 保证语义正确，不负责完成后续 normalization。
不要提前宣称已经优化： analyzed tree 的三个 WHERE 谓词仍集中在 join 上方，两个等值 ON 条件仍在 otherJoinConjuncts，alias wrapper 也仍存在。绑定完成不等于逻辑重写完成。
交给下一阶段的对象： Analyzer 将新 root 写回 CascadesContext.rewritePlan。 NereidsPlanner#planWithoutLock 在这里保存 analyzedPlan；若不是 ANALYZED EXPLAIN，就继续调用 whole-tree Rewriter。

SQL 语法结构不必是最适合搜索的结构；Rewriter 先做确定性、语义保持的树变换。

本 SQL 在 whole-tree rewrite 中发生的四类变化

1. alias wrapper 归一化

LogicalSubQueryAliasToLogicalProject 把 alias wrapper 改成 project，并把表别名写入 catalog relation。后续 project merge/pruning 继续清理只为别名服务的中间层。

2. filter pushdown

原来位于两层 join 上方的三个谓词分别移动到 customer、orders、lineitem 分支，使 scan 上方尽早减少行数。

3. hash condition 识别

FindHashConditionForJoin 把两个可用于等值 Hash Join 的 ON 条件 从 otherJoinConjuncts 移到 hashJoinConjuncts。

4. 列裁剪与初始 join 方向

ColumnPruning 只保留向上游需要的列； ReorderJoin 与 InitJoinOrder 可重建/交换 inner join， 本次结果成为 lineitem ⋈ (orders ⋈ customer)。

重写完成后的树

LogicalResultSink
└─ LogicalSort
   └─ LogicalProject(result columns)
      └─ LogicalJoin(hash=[o_orderkey = l_orderkey])
         ├─ Project(L_ORDERKEY, L_LINENUMBER)
         │  └─ Filter(l_shipdate > ...)
         │     └─ OlapScan(lineitem, operativeCol=[...])
         └─ Project(C_CUSTKEY, O_ORDERKEY, O_ORDERDATE)
            └─ LogicalJoin(hash=[c_custkey = o_custkey])
               ├─ Project(O_ORDERKEY, O_CUSTKEY, O_ORDERDATE)
               │  └─ Filter(o_orderdate < ...) → orders scan
               └─ Project(C_CUSTKEY)
                  └─ Filter(c_mktsegment = ...) → customer scan
分支 下推谓词 向上保留的业务列 scan operative columns
customer c_mktsegment = 'BUILDING' C_CUSTKEY C_CUSTKEY, C_MKTSEGMENT
orders o_orderdate < 1995-03-15 O_ORDERKEY, O_CUSTKEY, O_ORDERDATE 同左
lineitem l_shipdate > 1995-03-15 L_ORDERKEY, L_LINENUMBER L_ORDERKEY, L_LINENUMBER, L_SHIPDATE
join 左右方向不是稳定 API： 当前快照确实展示 lineitem ⋈ (orders ⋈ customer)，但方向受统计与 session 状态影响。稳定结论是 rewrite 能 flatten/rebuild inner-join cluster，并能按估计交换 children， 不是某个固定表永远在左侧。
交给下一阶段的对象： 这棵 tree 仍然只有 LogicalJoin、LogicalSort 等“算什么”的节点， 没有 Hash Join implementation、distribution、enforcer 或 cost。 NereidsPlanner#optimize 会把它送入 Memo。

04

MEMO PLAN：从一棵逻辑树扩展成共享候选图

这里同时发生等价变换、物理实现、统计派生、属性请求、成本比较与 enforcer 搜索。

输入Rewritten LogicalPlan
搜索容器Memo
调度单位Job / LIFO stack
最优解Best(Group, Property)

第一步：tree 进入 Memo

NereidsPlanner.optimize
└─ new Optimizer(cascadesContext).execute()
   └─ CascadesContext.toMemo()
      └─ new Memo(connectContext, rewrittenPlan)
         └─ Memo.init(plan)                  // 自底向上
            ├─ child plan → child Group
            ├─ replaceChildrenToGroupPlan
            ├─ new GroupExpression(operator, childGroups)
            └─ new Group(groupId, groupExpression, logicalProperties)
Memo 持有 root、所有 Groups、全局 GroupExpression 去重表；通过 copyIn 插入新候选。
Group 一个逻辑等价结果；保存 logical/physical expressions、enforcers、statistics 与 lowestCostPlans。
GroupExpression 一个 plan operator 加 child Group 引用；按 property 保存 cost、child requests 与输出属性。
为什么 Memo 是 DAG： 多个候选可以复用同一个 child Group，不必各自复制完整子树。 Rule 负责保证新表达式语义等价；Memo 负责存储、去重、合并与复用，不会重新证明 SQL 等价性。

第二步：JobStack 驱动搜索

Optimizer.execute
├─ DeriveStatsJob(root logical expressions)
├─ SimpleJobScheduler.executeJobPool()
└─ OptimizeGroupJob(root, required = GATHER)
   ├─ OptimizeGroupExpressionJob(logical GroupExpression)
   │  ├─ exploration rules
   │  └─ implementation rules
   │     └─ ApplyRuleJob
   │        ├─ GroupExpressionMatching
   │        ├─ Rule.transform
   │        └─ Memo.copyIn(newPlan, ownerGroup, false)
   └─ CostAndEnforcerJob(physical GroupExpression)

SimpleJobScheduler 不启动并行 task pool，而是不断从 JobStack 执行 pop()；所以实际是单线程 LIFO continuation。 ApplyRuleJob 产生 logical result 时会继续派生统计并探索，产生 physical result 时会进入 CostAndEnforcerJob。

第三步：这条 SQL 的搜索空间具体在比较什么

逻辑等价候选

exploration rules 为 inner joins 生成合法的 commute/associate 等价结构。 Group 代表同一个关系结果，GroupExpression 代表不同求法。

物理 implementation

LogicalJoinToHashJoin 生成 PhysicalHashJoin； LogicalSortToPhysicalQuickSort 生成两阶段 sort 和 gather-sort 候选。

属性与 enforcer

Hash Join 请求 broadcast 或左右 hash distribution；ORDER BY 请求 order + gather。 缺口由 PhysicalDistribute / sort enforcer 补齐并计入成本。

Stats、properties、cost 怎样汇合

CostAndEnforcerJob.execute
├─ RequestPropertyDeriver.getRequestChildrenPropertyList
├─ OptimizeGroupJob(child, childRequiredProperty)
├─ CostCalculator.calculateCost(operator)
├─ CostCalculator.addChildCost(...)
├─ ChildrenPropertiesRegulator.adjustChildrenProperties
├─ ChildOutputPropertyDeriver.getOutputProperties
├─ recordPropertyAndCost
│  ├─ GroupExpression.lowestCostTable
│  └─ Group.lowestCostPlans
└─ output 不满足 required property
   └─ EnforceMissingPropertiesHelper.enforceProperty
      ├─ sort / distribution enforcer
      └─ enforcer cost + child cost → 再比较
“一个 Group 一个 best plan”是错的： 正确状态是 Best(G, P)。同一个 orders/customer Group 在 ANY、REPLICATED、按 o_orderkey hash 等不同 required property 下可以有不同赢家。

从本次 Memo 看获胜决策

语义层 主要候选 本次获胜方案 上层为什么需要它
orders ⋈ customer 左右方向、不同 child distributions orders probe + replicated customer build customer 过滤后较小，broadcast network cost 可接受。
lineitem ⋈ 上述子树 左右方向、broadcast/hash/bucketed requests lineitem probe + orders 子树按 orderkey STORAGE_BUCKETED 与 lineitem 的 bucket layout 对齐。
ORDER BY GATHER_SORT；LOCAL_SORT + GATHER + MERGE_SORT 两阶段 sort 先局部排序，再汇聚并归并有序流。
root result root property entries GATHER 下的最低成本 ResultSink 路径 结果需要返回单个 MySQL client。
MEMO PLAN 是“搜索完成后的 Memo”： 输出已经含 Chosen Expression、BEST 和 chosen properties， 末尾还追加 optimized physical tree。它不是 copy-out 之前、尚未选赢家的原始中间快照。
交给下一阶段的状态： root Group 已经在要求的 GATHER property 下保存最低成本入口； 每个获胜 GroupExpression 也记录了 children 所需 properties。Planner 可以沿这些指针递归 copy-out。

05

从 Memo 递归取出获胜 PhysicalPlan

Memo 保存的是共享图；执行层需要的是一棵具体树，所以 Planner 必须按 property 递归 copy-out。

起点root Group + GATHER
选择表lowestCostPlans
产物PhysicalPlan tree
尾处理PlanPostProcessors
NereidsPlanner.chooseNthPlan(root, GATHER, nth)
└─ chooseBestPlan(root, GATHER, cascadesContext)
   ├─ Group.getLowestCostPlan(requiredProperty)
   ├─ 标记 chosen expression / property / enforcer
   ├─ GroupExpression.getInputPropertiesList(requiredProperty)
   ├─ 对每个 child Group 递归 chooseBestPlan
   ├─ groupExpression.getPlan().withChildren(chosenChildren)
   ├─ withGroupExpression(...)
   └─ withPhysicalPropertiesAndStats(...)
└─ NereidsPlanner.postProcess
   └─ PlanPostProcessors.process(physicalPlan)

每一层都必须携带 required property：父节点用获胜 GroupExpression 记录的 ChildrenRequires 决定如何递归选择孩子。若获胜入口是 enforcer， copy-out 先得到 enforcer，再按它的 child property 回到同一个 owner Group 取出被强制前的最佳子计划。

runtime filter 的时机： PlanPostProcessors 在 copy-out 后生成/裁剪 runtime filters。 因此 PHYSICAL 输出中的 RF0..RF3 属于最终物理树后处理结果， 不是 Memo 中 join-order/cost 搜索的原始输入。

PhysicalResultSink

   └─ PhysicalDistribute[GATHER]
      └─ PhysicalQuickSort[LOCAL_SORT]
         └─ PhysicalProject
            └─ PhysicalHashJoin(lineitem ⋈ orders/customer, bucket shuffle)
               ├─ lineitem scan → filter → project
               └─ PhysicalDistribute[STORAGE_BUCKETED(o_orderkey)]
                  └─ PhysicalHashJoin(orders ⋈ customer, broadcast)
                     ├─ orders scan → filter → project
                     └─ PhysicalDistribute[REPLICATED]
                        └─ customer scan → filter → project
交给下一阶段的对象： 一棵已经带有 physical properties、statistics、GroupExpression 引用和 runtime filters 的 PhysicalPlan。SHAPE 与 PHYSICAL 只观察它；DISTRIBUTED 才继续改变表示。

SHAPE 与 PHYSICAL：同一赢家的两种观察方式

它们不是新的优化 pass；差别只是打印时保留多少信息。

MEMO PLAN 回答“还有哪些候选、每个 required property 谁最便宜、赢家要求孩子提供什么”。 适合解释 why。
SHAPE PLAN 调用 optimizedPlan.shape("")，隐去易变 ID、stats 与大部分属性细节。 适合先确认 what。
PHYSICAL PLAN 返回 scalar cost + optimizedPlan.treeString()，展示 explicit distribute、 Group、stats 与 RF。适合把 what 回查到 why。

这条 SQL 的 SHAPE 一眼告诉你什么

PhysicalQuickSort[MERGE_SORT]
--PhysicalDistribute[DistributionSpecGather]
----PhysicalQuickSort[LOCAL_SORT]
------hashJoin[INNER_JOIN bucketShuffle]
        ... lineitem
        ... hashJoin[INNER_JOIN broadcast]
              ... orders
              ... customer
  • join tree 是 lineitem ⋈ (orders ⋈ customer)；
  • 内层 join 广播 customer，外层 join 采用 bucket shuffle；
  • ORDER BY 使用 LOCAL_SORT → GATHER → MERGE_SORT。

PHYSICAL 再补上哪些证据

细节 示例 回查用途
Memo owner PhysicalHashJoin@11 回到 Memo 中相应 Group，看它击败了哪些候选。
statistics scan/filter/join 的估算行数 解释 cost 输入，不等于运行时实际行数。
distribution REPLICATED、STORAGE_BUCKETED、GATHER 解释为何稍后会产生三个 Exchange 边界。
runtime filters RF0..RF3 确认 post-process 给最终 Hash Join/Scan 建立的过滤通道。
scalar cost 1658520.324... 候选排序标尺，不是毫秒预测。
推荐阅读顺序： 先用 SHAPE 确认稳定骨架，再用 PHYSICAL 找 Group/property/stats， 最后回到 MEMO 查 loser candidates 与 ChildrenRequires。 不要把三份大输出都从第一行顺读到底。

先翻译和切分 fragments

NereidsPlanner.distribute(physicalPlan, explainLevel)
├─ splitFragments(physicalPlan)
│  ├─ new PlanTranslatorContext(...)
│  └─ PhysicalPlanTranslator.translatePlan(physicalPlan)
│     ├─ PhysicalOlapScan  → OlapScanNode
│     ├─ PhysicalHashJoin  → HashJoinNode

visitPhysicalDistribute 把 CBO 中的 property enforcer 变成执行图边界： upstream fragment 通过 DataStreamSink 发送数据，downstream fragment 以 ExchangeNode 接收。没有 Exchange 边界的 scan/filter/project/join 会继续留在同一个 fragment 内。

Nereids PhysicalPlan Translator 产物 本 SQL 中的表现
DistributionSpecReplicated UNPARTITIONED sender + Exchange customer 从 fragment 3 广播到 fragment 2。

PhysicalQuickSort[MERGE_SORT] Exchange merge-sort metadata 根端打印为 VMERGING-EXCHANGE。

本次教学环境设置 parallel_pipeline_task_num=1 且只有一个 BE， 所以四个 fragment 各展示一个 instance，并全部落到同一 BackendWorker。 这是采样环境事实，不是分布式规划器保证的固定形状。
