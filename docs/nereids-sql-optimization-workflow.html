Doris Nereids 优化器

不从类清单开始，而是固定一条三表 SQL，跟着它依次变成未绑定逻辑树、已分析逻辑树、 重写后的逻辑树、Memo 中的候选图、获胜的 PhysicalPlan，以及最终的 fragments、exchanges 和 worker instances。每一层都回答四件事：入口在哪里、对象变了什么、源码怎样继续、下一层拿到什么。

七份输出不等于七次变换 SHAPE 与 PHYSICAL 是同一棵获胜 PhysicalPlan 的两种渲染，不是两个串行优化阶段。

先把“处理阶段”和“观察视图”分开

一次普通查询的核心对象只沿下面的主链迁移。EXPLAIN 在不同边界提前返回或选择不同打印器， 因而让我们看到各层状态。本文不介绍 LOGICAL PLAN PROCESS、Nereids trace 或 DPHyp trace 等日志型输出。

  1. SQL / ExplainCommandparser 先得到命令 AST，再把内部 query plan 交给 NereidsPlanner。
  2. Parsed LogicalPlanUnboundRelation、UnboundSlot、SQL 原始 join 骨架。
  3. Analyzed LogicalPlanrelation、slot、类型、ExprId 与语义约束已经绑定。
  4. Rewritten LogicalPlan谓词下推、列裁剪、join 归一化后，成为 CBO 输入。
  5. Memo DAGGroup 保存等价结果，GroupExpression 保存候选关系表达式。
  6. Chosen PhysicalPlan按 required property 递归取出最低成本物理树，再做 post-process。
  7. Shape / Physical views同一棵 PhysicalPlan 的紧凑视图和详细视图。
  8. DistributedPlan graphPhysicalDistribute 翻译成 Exchange/fragment，再分配 worker instances。
最重要的源码事实： NereidsPlanner#getExplainString 对 SHAPE 调用 optimizedPlan.shape("")，对 PHYSICAL 返回 cost + optimizedPlan.treeString()。它们共享同一个 optimizedPlan 字段。

The single running example

全文只跟这一条三表 SQL

查询使用 TPC-H 的 customer、orders、lineitem， 但刻意去掉聚合与 LIMIT，只保留三表连接、三个单表过滤、四列投影和 ORDER BY。 这样每次树变化都能在十五行左右的逻辑输出中看清。 

SELECT
    c.c_custkey,
    o.o_orderkey,
    l.l_linenumber,
    o.o_orderdate
FROM customer c
JOIN orders o
  ON c.c_custkey = o.o_custkey
JOIN lineitem l
  ON o.o_orderkey = l.l_orderkey
WHERE c.c_mktsegment = 'BUILDING'
  AND o.o_orderdate < DATE '1995-03-15'
  AND l.l_shipdate > DATE '1995-03-15'
ORDER BY o.o_orderdate, o.o_orderkey, l.l_linenumber;

主线采用普通 Cascades

配套目录同时保存 Cascades 与显式 DPHyp 结果；本文固定使用 cascades.txt，即 enable_dphyp_optimizer=false。 DPHyp 会改变 join-order 分支，但不会改变 parser → analyzer → rewrite → physical copy-out → distribute 这条外层流水线。

不要固定易变 ID

文中的 PlanId、ExprId、GroupId、tablet/instance ID 和 cost 只用于解释本次快照。 稳定事实是对象类型、调用关系、property 语义和数据流，不是某个具体编号。

Optimizer-focused recursive reduction

从 planWithLock 开始，递归压缩到真正的优化循环

NereidsPlanner 同时承担 Explain 截断、profile、trace、minidump、SQL cache、 资源管理和计划生成。直接顺读源码容易让控制逻辑淹没优化器主线。下面每深入一层， 都只保留会改变计划表示、扩展候选空间、传递物理属性或生成分布式执行图的调用。 第 0 层额外保留 collect/lock/release，因为它们界定优化所依赖的稳定元数据快照。

伪代码约定： 这些代码用于表达源码语义，不是可直接替换的 Java 重构。真实实现把中间 plan 写回 CascadesContext.plan，这里改成显式返回值；同时固定本文路径为普通 SELECT、普通 Cascades、默认 nth=1，不展开 CTE、DPHyp、指定 GroupId 和各种 Explain/日志分支；MV 只保留它作为 side candidate 进入 Memo 的边界语义。

第 0 层：规划生命周期外壳

private PhysicalPlan planWithLock(
        LogicalPlan parsedPlan,
        PhysicalProperties required) {
    try {
        LogicalPlan plan = preprocess(parsedPlan);
        CascadesContext context = initCascadesContext(plan, required);

        collectAndLockTable(context);
        return planWithoutLock(context, required);
    } finally {
        statementContext.releasePlannerResources();
    }
}

普通查询的 required 由 buildInitRequireProperties() 初始化为 PhysicalProperties.GATHER。它不是外围参数噪声：后面的搜索必须为 root 找到满足 GATHER 契约的最低成本计划；该契约如何继续传给 ResultSink 的 child 仍可能受 parallel result sink 等执行能力影响。

这个外壳保留什么

  • preprocess：Analyzer 之前的窄范围修正。
  • initCascadesContext：建立 plan、JobStack、RuleSet 与 root required property 的共同工作区。
  • collectAndLockTable：在稳定元数据视图下完成分析和优化。
  • finally：无论成功还是异常都释放表锁等 planner resources。

这个外壳删掉什么

  • ExplainLevel 的各个提前返回。
  • plan process、trace、profile 与 debug log。
  • minidump 输入输出和 SQL cache 快速路径。
  • 测试用 nth plan、required GroupIds 等诊断入口。
planWithoutLock 这个名字容易误读： 它表示“该方法自己不负责加锁”，不是“调用它时没有锁”。真实路径先在 collectAndLockTable 中加锁，再调用 planWithoutLock， 直到外层 finally 才释放；实际源码中的 callback 也在释放资源之前执行。

第 1 层：把 planWithoutLock 压成六个状态变换

private PhysicalPlan planWithoutLock(
        CascadesContext context,
        PhysicalProperties required) {
    LogicalPlan analyzed = analyze(context.getRewritePlan());
    LogicalPlan rewritten = rewrite(analyzed);

    // 不替换主 rewritten tree，只可能产生稍后 copyIn Memo 的候选
    List<LogicalPlan> mvAlternatives =
            preMaterializedViewRewrite(rewritten);

    Memo memo = optimize(rewritten, mvAlternatives, required);
    PhysicalPlan chosen =
            chooseBestPlan(memo.getRoot(), required);
    return postProcess(chosen);
}
核心调用 输入 → 输出 这条三表 SQL 的可见变化
analyze Unbound tree → Bound logical tree 三张表、所有 slot、类型、ExprId、sink 与表达式获得真实语义。
rewrite Bound tree → Normalized logical tree 谓词下推、列裁剪、hash condition 识别并初始化 join 方向。
preMaterializedViewRewrite Main tree → Optional side candidates 本次快照未显示 MV alternative，主线按 no-op 阅读。
optimize Logical tree → Memo with costed alternatives join order、Hash Join、broadcast/bucket/gather 与 sort 候选共同搜索。
chooseBestPlan Memo DAG → One PhysicalPlan tree 从 Best(root, GATHER) 沿 child properties 递归 copy-out。
postProcess Chosen tree → Final PhysicalPlan 清理物理树；本快照启用 RF，因而生成并裁剪 RF0..RF3；最后校验。
主计划表示只在两类载体间切换： Analyzer 与 Rewriter 阶段的主计划是一棵写在 CascadesContext.plan 中的 tree； Optimizer.execute() 调用 toMemo() 后，搜索状态才变成 Memo → Group → GroupExpression 组成的 DAG。不要在 Analyze 阶段寻找 Group， 也不要把 Memo 当成普通 Plan tree。

第 2 层 A：preprocess 与元数据稳定边界

preprocess：顺序执行两个 visitor 
LogicalPlan preprocess(LogicalPlan plan) {
    for (PlanPreprocessor processor : List.of(
            new TurnOffPageCacheForInsertIntoSelect(),
            new PullUpSubqueryAliasToCTE())) {
        plan = processor.rewriteRoot(plan, statementContext);
    }
    return plan;
}

第一条只影响 INSERT/file/table sink；第二条只把包含 LEADING hint 的 subquery alias 提升为 CTE。本文是普通 SELECT， customer c 等也没有这类 hint，因此这一步返回与 parsed plan 等价的树。它不是 filter pushdown、join reorder 或 Memo 优化。

collectAndLockTable：收集真实表，但不绑定主计划 
void collectAndLockTable(CascadesContext context) {
    // AddInitMaterializationHook → CollectRelation → PreloadExternalMetadata
    context.newTableCollector(true, true).collect();
    if (normalExecution) {
        waitForTimeBasedChangeVisibleBeforeLock();
    }

    statementContext.lock();        // 内部按 TableIf.id 排序
    context.setCteContext(new CTEContext());
}

collector 遍历 UnboundRelation、view、CTE、subquery 与 sink， 把真实 TableIf 缓存在 StatementContext；它不会把主树的 UnboundRelation 改成 scan，那仍是 Analyzer 的工作。对本文 SQL， 这里确认 customer、orders、lineitem，并按 table id 顺序取得规划期读锁。 最后“使用新 context”具体只是重置 collector 临时使用的 CTEContext，不是重新创建整个 CascadesContext。

第 2 层 B：Analyze 与 Rewrite 共用 batch 执行骨架

Plan runBatches(Plan root, List<RewriteJob> jobs) {
    context.setRewritePlan(root);
    for (RewriteJob job : jobs) {
        JobContext jobContext = context.getCurrentJobContext();
        do {
            jobContext.setRewritten(false);
            job.execute(jobContext);       // top-down / bottom-up / custom
        } while (!job.isOnce() && jobContext.isRewritten());
    }
    return context.getRewritePlan();
}

LogicalPlan analyze(LogicalPlan parsed) {
    return (LogicalPlan) runBatches(parsed, Analyzer.ANALYZE_JOBS);
}

LogicalPlan rewrite(LogicalPlan analyzed) {
    return (LogicalPlan) runBatches(
            analyzed, Rewriter.WHOLE_TREE_REWRITE_JOBS);
}

浅树由 visitor 递归遍历，过深时 adaptive job 会切换到显式 JobStack，避免 Java 调用栈过深；无论实现形式如何，本质仍是 top-down 或 bottom-up 地把规则应用到整棵树。

bottomUp([
  BindRelation,

]);

BindExpression 也负责把查询的 UnboundResultSink 变成 LogicalResultSink； Analyzer 中名为 BindSink 的 job 主要处理 INSERT/file 等 sink。

本 SQL 的 Rewrite 可压成

normalize aliases;
push filters to scans;
move equi-join predicates to hash;
prune unused columns;
initialize join directions;
finalize logical properties;

whole-tree Rewriter 以启发式规则为主，也包含 stats 驱动或可选 cost-based rewrite；它不是单纯的语法整理器。

pre-MV 是旁路，不是主树替换： 命中时，它将规则优化并归一化后的 MV 方案写入 StatementContext.rewrittenPlansByMv。随后 CascadesContext.toMemo() 才把这些候选 copyIn root Group； cascadesContext.getRewritePlan() 仍指向主 RBO tree。

第 2 层 C：Optimizer.execute 只剩 Memo 初始化、统计与 root 搜索

Memo optimize(
        LogicalPlan rewritten,
        List<LogicalPlan> alternatives,
        PhysicalProperties required) {
    Memo memo = new Memo(rewritten);       // Memo.init 递归建初始 Groups
    copyAlternativesIntoRoot(memo, alternatives);

    deriveStats(memo.getRoot());
    optimizeGroup(memo.getRoot(), required);
    return memo;
}

当前路径没有 CTE，也固定使用普通 Cascades，所以 Optimizer.execute() 中的 CTE inline alternative 与 DPHyp 分支可以从主线拿掉。 初始 rewritten tree 进入 Memo 后，每个节点先对应一个 Group；新规则结果通过 Memo.copyIn 加入等价 Group，公共 child Group 因而可以被多个候选共享。

第 3 层：把 JobStack 还原成递归的 Cascades 搜索

void optimizeGroup(Group group, PhysicalProperties required) {
    if (group.hasBestPlan(required)) {
        return;
    }

    for (GroupExpression logical : group.logicalExpressions()) {
        optimizeGroupExpression(logical, required);
    }
    for (GroupExpression physical : group.physicalExpressions()) {
        costAndEnforce(physical, required);
    }
}

void optimizeGroupExpression(
        GroupExpression expression,
        PhysicalProperties required) {
    for (Rule rule : explorationRules + implementationRules) {
        for (Plan result : rule.transform(matches(rule, expression))) {
            CopyInResult copied =
                    memo.copyIn(result, expression.ownerGroup());
            if (!copied.generatedNewExpression()) {
                continue;
            }
            GroupExpression candidate = copied.expression();

            if (candidate.isLogical()) {
                deriveStats(candidate);
                optimizeGroupExpression(candidate, required);
            } else {
                costAndEnforce(candidate, required);
            }
        }
    }
}

void costAndEnforce(
        GroupExpression expression,
        PhysicalProperties required) {
    for (List<PhysicalProperties> childRequests
            : deriveChildPropertyAlternatives(expression)) {
        for (int i = 0; i < expression.arity(); i++) {
            optimizeGroup(expression.child(i), childRequests.get(i));
        }

        Cost total = operatorCost(expression)
                + lowestChildCosts(expression, childRequests);
        PhysicalProperties output =
                deriveOutputProperties(expression, childRequests);

        recordCandidate(expression, output, childRequests, total);
        if (output.satisfy(required)) {
            recordAsSatisfying(
                    expression, required, output, childRequests, total);
        } else {
            addAndCostEnforcer(expression.ownerGroup(), output, required);
        }
    }
}
这是语义递归，不是源码调用顺序的逐行复刻： 源码把 continuation 压入单线程 LIFO JobStack，exploration、 implementation、统计派生与 cost job 会交错执行。两类 rule 都通过 ApplyRuleJob；不是“先完成全部 exploration，再统一 implementation”。

对本文 SQL，RequestPropertyDeriver 会为 Hash Join 枚举 broadcast、 hash/bucket 等 child requirements；root 的 GATHER 以及排序算子的语义 又会引入 gather 和两阶段 sort。每个 Group 保存的是 Best(Group, requiredProperty)，而不是一个脱离 property 的全局 best。 

Group.lowestCostPlans:
  requiredProperty
    → (lowestTotalCost, winningGroupExpression)

GroupExpression.lowestCostTable:
  requiredProperty
    → (totalCost, childRequiredProperties)

第 4 层：按 property 递归 copy-out，而不是“遍历所有候选再挑一次”

PhysicalPlan chooseBestPlan(
        Group group,
        PhysicalProperties required) {
    GroupExpression best = group.getLowestCostPlan(required);
    markChosen(group, best, required);

    List<PhysicalProperties> childRequests =
            best.getInputPropertiesList(required);
    List<Plan> children = new ArrayList<>();
    for (int i = 0; i < best.arity(); i++) {
        children.add(chooseBestPlan(
                best.child(i), childRequests.get(i)));
    }

    return best.getPlan()
            .withChildren(children)
            .withGroupExpression(best)
            .withPhysicalPropertiesAndStats(required, group.getStatistics());
}

cost 阶段已经把“这个 required property 下谁最便宜、它要求每个 child 提供什么” 写进 Group 与 GroupExpression。copy-out 只沿这些获胜指针递归恢复一棵 tree； 默认 nth=1 才走这条 chooseBestPlan 路径， nth>1 的诊断模式改走 Memo.rank/unrank。

第 5 层：PhysicalPlan 定型，然后才进入分布式计划

PhysicalPlan postProcess(PhysicalPlan plan) {
    plan = cleanupPhysicalTree(plan);
    plan = recomputePropertiesAndExecutionAnnotations(plan);
    if (runtimeFilterMode != OFF) {
        plan = generateRuntimeFilters(plan);
        if (enableRuntimeFilterPrune) {
            plan = pruneRuntimeFilters(plan);
        }
    }
    validate(plan);
    return plan;
}

FragmentIdMapping<DistributedPlan> distribute(PhysicalPlan plan) {
    PlanTranslatorContext translation =
            new PlanTranslatorContext(cascadesContext);
    PlanFragment root =
            new PhysicalPlanTranslator(translation, statsErrorEstimator)
                    .translatePlan(plan);
    List<PlanFragment> fragments = translation.getPlanFragments();
    FragmentIdMapping<DistributedPlan> graph =
            new DistributePlanner(
                    statementContext, fragments, false, false).plan();
    maybeAddLocalExchange(graph);
    return graph;
}

postProcess 不再搜索新的 join order；它顺序清理获胜物理树、补执行期标记、 按会话配置生成/裁剪 runtime filters 并校验。真正离开 Nereids IR 的边界是 PhysicalPlanTranslator：它先得到 PlanNode/PlanFragment graph， DistributePlanner 再为 fragments 选择 workers、scan ranges 与 instances。

源码中的四种“递归”不要混在一起

递归 递归单位 停止条件 本 SQL 中解决的问题
tree rewrite Plan node + children 节点无 child，或规则达到 fixpoint 从叶到根绑定 slot，并把谓词推到三张 scan。
Memo init/copyIn Plan node → child Groups 叶子 relation 把单棵 join tree 变成可共享、可扩展的候选 DAG。
property optimization Best(Group, Property) 该 property 已有 best，或候选被剪枝 比较 broadcast、bucket shuffle、gather 与各自 child 要求。
best-plan copy-out Chosen GroupExpression + child property 物理叶节点 恢复 lineitem ⋈ (orders ⋈ customer) 的唯一获胜物理树。

本 SQL 在 whole-tree rewrite 中发生的四类变化

1. alias wrapper 归一化

LogicalSubQueryAliasToLogicalProject 把 alias wrapper 改成 project，并把表别名写入 catalog relation。后续 project merge/pruning 继续清理只为别名服务的中间层。

2. filter pushdown

原来位于两层 join 上方的三个谓词分别移动到 customer、orders、lineitem 分支，使 scan 上方尽早减少行数。

3. hash condition 识别

FindHashConditionForJoin 把两个可用于等值 Hash Join 的 ON 条件 从 otherJoinConjuncts 移到 hashJoinConjuncts。

4. 列裁剪与初始 join 方向

ColumnPruning 只保留向上游需要的列； ReorderJoin 负责 flatten/rebuild 谓词相连的 inner-join cluster， InitJoinOrder 再按统计交换左右 children。本次最终方向 lineitem ⋈ (orders ⋈ customer) 来自 InitJoinOrder 的交换。

pre-MV 不改这里展示的主树： 命中时，preMaterializedViewRewrite 将 MV 方案写入 StatementContext.rewrittenPlansByMv，等到 toMemo() 再 copyIn root Group。LOGICAL PLAN 仍打印 cascadesContext.getRewritePlan() 指向的主 RBO tree。

visitPhysicalDistribute 把 CBO 中的 property enforcer 变成执行图边界： upstream fragment 通过 DataStreamSink 发送数据，downstream fragment 以 ExchangeNode 接收。没有 Exchange 边界的 scan/filter/project/join 会继续留在同一个 fragment 内。这是本文三表计划的切分规律；通用 translator 对 set operation、CTE 等节点还存在其他 fragment 构造或合并路径。 

PlanFragment translate(PhysicalPlan node) {
    if (node is PhysicalOlapScan) {
        return new PlanFragment(new OlapScanNode(node));
    }
    if (node is PhysicalDistribute) {
        PlanFragment upstream = translate(node.child());
        ExchangeNode receiver = new ExchangeNode(node.distributionSpec());
        PlanFragment downstream = new PlanFragment(receiver);
        upstream.setSink(new DataStreamSink(receiver));
        downstream.addChild(upstream);
        return downstream;
    }
    if (node is PhysicalHashJoin) {
        PlanFragment right = translate(node.right());
        PlanFragment left = translate(node.left());
        return mergeAtHashJoin(left, right, node);
    }
    if (node is PhysicalResultSink) {
        PlanFragment root = translate(node.child());
        root.setSink(new ResultSink());
        return root;
    }
    if (node is PhysicalQuickSort) {
        PlanFragment child = translate(node.child());
        if (node.phase == MERGE_SORT) {
            if (child.getPlanRoot() is ExchangeNode) {
                attachMergeInfoToReceivingExchange(child);
                markSenderSinkAsMerge(child);
            }
        } else { // LOCAL_SORT / GATHER_SORT
            child.addPlanRoot(new SortNode(node, child.getPlanRoot()));
        }
        return child;
    }
    if (node is other unary operator) {
        PlanFragment child = translate(node.child());
        child.setPlanRoot(translateOperator(node, child.getPlanRoot()));
        return child;
    }
}

本次教学环境设置 parallel_pipeline_task_num=1 且只有一个 BE， 所以四个 fragment 各展示一个 instance，并全部落到同一 BackendWorker。 这是采样环境事实，不是分布式规划器保证的固定形状；同样因为每个 BE 只有一个 instance，可选的 local-exchange pass 在本快照中没有产生可见节点。

看到 PlanNode 不等于回退旧优化器： PhysicalPlanTranslator 将已经选好的 Nereids PhysicalPlan 翻译为 org.apache.doris.planner.PlanNode、PlanFragment 和 org.apache.doris.analysis.Expr，是复用 FE/BE 执行协议的边界， 不是再次调用一套旧优化器。
最终产物： DISTRIBUTED PLAN 同时展示 fragment 内的执行 PlanNode 树、 fragment 之间的 Exchange 链、每个 fragment 的 unassigned/assigned job， 以及具体 worker/instance/scan ranges。至此，一条 SQL 完成从语义树到可下发执行图的转换。
