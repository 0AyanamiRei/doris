优化器入口：SQL 到物理计划的主链路

普通客户端请求通常已经在 ConnectProcessor 中完成解析；进入 StmtExecutor 后，parseByNereids() 会因为已有 parsedStmt 而早退。

三个上下文，三种生命周期

ConnectContext

连接/会话级：SessionVariable、query id、executor、环境和运行期状态。

StatementContext

单条语句级：ID generators、CTE/MV 状态、表与锁、统计缓存、planner hooks。

CascadesContext

单次优化级：rewrite plan、Memo、RuleSet、JobStack、当前 required properties。

三层 distribution 不要混：NereidsPlanner#buildInitRequireProperties() 当前给根计划提出 PhysicalProperties.GATHER 要求。随后依次是：① CBO 中的 PhysicalProperties 与 enforcer；② PhysicalDistribute 翻译成 Exchange/fragment；③ DistributePlanner 把 fragment 分给具体 worker/instance。
解析与 legacy fallback 的准确边界

ConnectProcessor#parseWithFallback 回退的是“dialect 转换后的 SQL → 原始 SQL”，两次仍使用 Nereids parser。当前普通 query 规划失败后没有再创建 legacy planner；enable_fallback_to_original_planner 已标为 removed。翻译成旧 PlanNode/PlanFragment 只是执行层数据结构兼容。

02 · Rule-based optimization

RBO 与 Rewrite Job：在计划树上收敛

Analyzer 与 Rewriter 都建立在 AbstractBatchJobExecutor 之上，但前者解决绑定与语义合法性，后者做一般逻辑等价改写。

NereidsPlanner.rewrite()
  → Rewriter.getWholeTreeRewriter(cascadesContext).execute()
    → AbstractBatchJobExecutor.execute()
      → TopicRewriteJob（条件分组 / 插入子 job）
      → AdaptiveTopDownRewriteJob / AdaptiveBottomUpRewriteJob
        ├─ 浅树：Visitor rewrite
        └─ 深树：RootPlanTreeRewriteJob → PlanTreeRewrite*Job → JobStack

Top-down

当前节点先反复匹配到稳定，再访问孩子。孩子变化不会自然回访父节点，适合“父形态决定向下改写”的规则。

Bottom-up

先孩子后父；父规则产生新树后会重新处理相关子树与父节点，更自然地达到子树固定点。

类型职责关键方法 / 注意点
RewriteJob批执行器看到的作业接口execute(JobContext)、isOnce()
RootPlanTreeRewriteJob树级入口与 Job scheduler 桥接创建根 RewriteJobContext，压入 top-down/bottom-up job
PlanTreeRewriteJob显式栈路径的逐节点 pattern match / transform它继承 Job，并不实现 RewriteJob
CustomRewriteJob运行整树 custom rewriter调用 CustomRewriter#rewriteRoot()
CostBasedRewriteJob对 apply/skip 两棵树分别继续 rewrite + optimize 后比成本它不是 Memo exploration rule
isOnce 的真实含义：它控制“批执行器是否因 JobContext.rewritten 再跑整批”，不是“每个节点只尝试一次规则”。浅树 visitor 与深树显式栈的 rewritten 标记路径存在实现差异，调试固定点问题时要先确认走了哪条 adaptive 分支。

Rule、Pattern 与 CBO 的边界

RuleFactory#buildRules() 产出 Rule；DSL 组合 pattern、when 和 then，最后绑定 RuleType。RBO 用 Pattern#matchPlanTree 匹配一棵具体树；CBO 的 GroupExpressionMatching 则枚举 Memo Group 中的组合。RuleType 也作为禁用位和“已应用规则”位。

03 · Memo & search

Memo、CBO、规则调度与 Join Reorder

Memo 的核心不是“缓存计划”，而是压缩搜索空间：Group 表示逻辑等价类，GroupExpression 表示一个算子及其有序子 Group。

Group A逻辑等价表达式
统一 logical properties / stats
GroupExpression
operator + ordered child groups
Group B / C作为 children
反向记录 parent expressions

Group 保存什么

  • logical / physical expressions
  • 单独的 enforcer 集合
  • Group 级 Statistics
  • required properties → (cost, best expression)

GroupExpression 保存什么

  • 算子与有序 child groups
  • owner Group 与 rule masks
  • properties → (cost, child requests)
  • 父请求到实际输出属性映射
Optimizer.execute()
  → CascadesContext.toMemo()
  → DeriveStatsJob(root)
  → [optional] JoinOrderJob / DPHyp → rebuild Memo → re-derive stats
  → OptimizeGroupJob(root, requiredProperties)
    → OptimizeGroupExpressionJob
      → ApplyRuleJob(exploration / implementation)
    → CostAndEnforcerJob
      → OptimizeGroupJob(child, childRequiredProperties)
      → cost + property regulation + enforcer

调度为什么像深度优先搜索

SimpleJobScheduler 从 JobStack 以 LIFO 顺序 pop/execute。Job 经常先压入“自己的 continuation”，再压入孩子或新候选，因此会先完成深层依赖，再回到上层继续计价。ApplyRuleJob 对新逻辑候选继续探索并派生统计；对物理候选进入计价。

去重与终止：Memo 用“operator + child Groups”的结构键去重；等价表达式落在不同目标 Group 时会合并 Group并修复父引用。GroupExpression.ruleMasks 避免同一 RuleType 在同一表达式上反复应用。

Join Reorder：两条路径最终汇合

Cascades rules

根据 disable/LEADING、统计可靠性、bushy 上限及 left-zig-zag 开关，选择 left-zig-zag、zig-zag 或 bushy exploration rules。

DPHyp

Optimizer#isDpHyp 根据连续 Join 数与开关进入 JoinOrderJob。Hypergraph 枚举失败会尝试 graph simplification；再失败保留原 Group。

定位 Join Reorder 路径时先看这些会话变量

disable_join_reorder、enable_dphyp_optimizer、max_table_count_use_cascades_join_reorder、max_join_number_of_reorder、enable_left_zig_zag、enable_bushy_tree、max_join_number_bushy_tree、dphyper_limit 与 join_order_time_limit。LEADING 成功后还会通过 context 状态关闭后续 reorder。

DPHyp 选出逻辑形状后会 copy-out、做必要 rewrite、释放并重建 Memo、重新派生统计，然后仍进入统一的 OptimizeGroupJob 物理优化链。

派生链

DeriveStatsJob 采用“先压 continuation，再压 children”的两阶段后序遍历；子 Group 有统计后，StatsCalculator#estimate() 访问当前 plan。Filter、Join、表达式分别委托给 FilterEstimation、JoinEstimation、ExpressionEstimation，最后把归一化后的统计放到 owner Group。

常见回退可以直接从源码读出：AND 逐项应用，OR 使用容斥；等值优先使用热点频率或 1 / NDV，范围谓词按 min/max 上的均匀分布估算，无法缩放时常回退到 0.5；LIKE 与 IS NULL 等也有固定默认选择率。这些是启发式估算，不是直方图 bucket lookup。

直方图的当前真实边界：统计子系统仍保留 HistogramTask、表结构、HistogramCacheLoader 与 StatisticsCache#getHistogram()；但 AnalysisManager#createTaskForEachColumns 当前把标准命令的列任务强制设为 FUNDAMENTALS，不会实例化 HistogramTask。同时，nereids/stats 没有读取 histogram API 的估算调用。Minidump 会抓取/回放 histogram，使问题现场完整，但这既不表示标准 ANALYZE 当前可达 histogram 采集，也不表示 FilterEstimation 已使用 bucket 选择率。

未知或异常统计如何影响 Join Reorder

StatsCalculator#disableJoinReorderIfStatsInvalid() 在真实规划环境中只检查三类情况：表 row count 为 -1；列 NDV 为 0 但 min/max 非空；或 NDV 大于 10 倍 row count。命中后以 statement-once 方式设置 disable_join_reorder 并记录原因。UNKNOWN、stale 标签或缺少分区统计本身不会一概关闭重排；一般估算异常在非 FE debug 模式会回退到 unknown stats 或第一个孩子的统计。

对已裁剪分区，只有所有选中分区的列统计均已知时才合并分区统计；任一 UNKNOWN 会让该列回退到表级统计。stale 健康度主要驱动自动重采集，优化器不会仅因 stale 标签拒绝现有列统计。

05 · Cost & selection

Cost Model 与计划选择

Cost Model 只计算“当前物理算子的局部 cost”。属性枚举、孩子递归、enforcer 与 best-plan 表由 CostAndEnforcerJob 组织。

标量成本：value = cbo_cpu_weight × CPU + cbo_mem_weight × Memory + cbo_net_weight × Network。三个分量先截到非负，再沿子树逐分量相加；当前 memory 分量不是峰值内存。CostWeight 中保留的 ioWeight、penaltyWeight 与 DELAY 并未进入这条主计算链。
算子主要 cost 信号（概括）容易忽略的细节
Scan / Filterscan 约随 row count；filter 与谓词/表达式成本和前缀索引命中有关当前 filter 局部 cost 不直接乘输入行数
Sort / TopNchild rows、output rows、networkGATHER 单阶段路径有明显 memory 惩罚
Aggregate输入行数、BE 数、local/global/bucketed 阶段、表达式成本global group-by 的 required distribution 会影响子属性
Hash Joinprobe/build/output rows、broadcast vs shuffle、build memory、并行实例semi/anti shortcut、runtime-filter 启发式、广播 build factor
Nested Loop Join近似 leftRows × rightRows 的 CPU右侧 memory 带形状相关惩罚
Distributerows、data size factor、BE 数、distribution 类型hash/replicated/gather/random 公式不同
 
CostAndEnforcerJob
  1. RequestPropertyDeriver → 多组 child required properties
  2. 对每个 child: 查 Group best；没有则递归 OptimizeGroupJob
  3. ChildrenPropertiesRegulator → 可行的实际 child outputs
  4. ChildOutputPropertyDeriver → 当前算子 output properties
  5. CostCalculator → local cost + child cost
  6. output 不满足 parent required → EnforceMissingPropertiesHelper
  7. 写 GroupExpression.lowestCostTable + Group.lowestCostPlans

从 best table 到最终物理树

NereidsPlanner#chooseBestPlan(Group, PhysicalProperties, CascadesContext) 读取 Group 在该 required property 下的最低成本表达式，再读取表达式保存的 child property requests，递归重建 children，最后附上 physical properties 与 Group statistics。nth_optimized_plan > 1 使用 Memo#rank/unrank 的调试路径；它不是无限、完整地枚举全部空间。

当前剪枝边界：主链没有完整的 lower-bound/upper-bound cost pruning；主要跳过点是某个 child property 没有可行 best，或 distribution-only enforcer 已明显劣于现有 best。

06 · History-based optimization

HBO：把运行历史接回下一次规划

HBO 是一个有门控、有指纹匹配、有限覆盖面的反馈环。它保留普通统计估算作为 delegate，历史命中时只替换特定节点的 row count，并在 Cost Model 中提供一个广播 Join 特例。

HboPlanInfoProvider

按 query id 暂存 PlanNodeId ↔ PhysicalPlan 双向映射及 scan predicate；服务本次执行反馈。

HboPlanStatisticsProvider

以 PlanNodeAndHash 为 key 保存 recent runs，并负责跨 FE 同步。

HboPlanStatisticsManager

由 Env 持有，聚合 info provider 与 statistics provider 的生命周期入口。

反馈闭环的五个关口

  1. 规划采集：NereidsPlanner#collectHboPlanInfo 在翻译后建立 Nereids plan id 与 legacy PlanNodeId 的映射；RBO 的 CollectPredicateOnScan 保存 scan 上谓词。
  2. 运行筛选：Profile 从单个 execution profile 的 merged runtime profile 生成节点运行统计，只为全局开启 collection、状态健康且耗时严格超过 Config.qe_slow_log_ms 的语句发布。
  3. 指纹与输入态：HboUtils 对计划树 fingerprint 做 SHA-256，并附带输入 OLAP scan statistics；直接作为 operand 的 literal 会参数化，函数内部 literal 刻意保留。scan 指纹包含表、RelationId、裁剪分区数量与 visible version/time。recent-runs 以 FIFO 保存。
  4. 下次匹配：DeriveStatsJob 在 enable_hbo_optimization 下改用 HboStatsCalculator；filter-on-scan、join、aggregate 命中时替换输出 row count。匹配依次尝试 FULL、PARTITION_AND_OTHER；仅开启 non-strict 后再尝试 PARTITION_ONLY。
  5. 成本特例：广播 hash join 匹配到历史 build/probe skew 且超过阈值时，CostModel 下调 probe shortcut factor；HBO 并未重写全部成本公式。
匹配失败是正常路径：计划形状、hash、输入表统计状态、RF-safe 检查、健康检查或缓存生命周期任一不满足，就继续使用普通 StatsCalculator/CostModel。列统计不会因 HBO row count 命中而整体替换。历史与 query 临时信息都是 FE 内存软引用缓存，会过期、可被 GC，且 FE 重启后丢失；没有模型训练或磁盘持久化。
当前版本的 HBO 配置与测试陷阱

采集由 GLOBAL enable_hbo_info_collection 控制，使用由 session enable_hbo_optimization 控制；两者默认关闭。当前实际慢查询门槛是 qe_slow_log_ms。部分 regression case 仍设置旧名 hbo_slow_query_threshold_ms，阅读或修复测试时应以当前 Profile#isSlowQueryForHbo 和 Config 为准。

EXPLAIN level 的准确映射

测试助手

PlanChecker 提供 parse → analyze → rewrite → optimize 的链式入口，也能单独 applyTopDown / applyBottomUp、deriveStats、applyExploration / applyImplementation、检查 Memo Group 数和匹配物理 plan pattern。MemoTestUtils 则提供 Connect/Statement/CascadesContext 与合法 Memo 的轻量构造。它们是学习单条规则最短的可执行路径。

run-fe-ut.sh --run 还支持 pkg.Class#method1+method2 选择方法，以及逗号分隔多个类；run-regression-test.sh --run -f path/to/case.groovy 会自动转换为对应的 -d 与 -s。

Reading route

推荐阅读顺序

  1. 先看总控，不下钻规则。读 NereidsPlanner#plan / planWithLock / planWithoutLock，手写出阶段顺序与早退点。
  2. 跟一条最小 SQL 完成 parse + bind。读 NereidsParser#parse、LogicalPlanBuilder、Analyzer，观察 UnboundRelation 如何消失。
  3. 掌握一种 RBO traversal。从一个简单 RuleFactory 进入 AdaptiveBottomUpRewriteJob，对照 visitor 与显式 JobStack。
  4. 建立 Memo 不变量。读 Memo#copyIn、Group、GroupExpression#equals，再看 Group merge。
  5. 沿 JobStack 走一次 CBO。依次看 OptimizeGroupJob → OptimizeGroupExpressionJob → ApplyRuleJob → CostAndEnforcerJob。
  6. 补上统计与成本。从 DeriveStatsJob 到 StatsCalculator，再从 CostCalculator 到具体 visitor 公式。
  7. 最后看搜索空间与反馈。分别跟踪 DPHyp 的 Memo 重建，以及 HBO 的“本次 Profile → 下次 DeriveStats”闭环。
  8. 以翻译和执行收尾。读 chooseBestPlan、PhysicalPlanTranslator、DistributePlanner，完成端到端心智模型。

Hands-on

从浅到深的调试练习

练习 1 · 看见 Unbound → Bound

SQL：单表投影 + filter。断点：NereidsParser#parse、BindRelation、BindExpression。观察 relation/slot 类型与 ExprId 何时确定。

练习 2 · 跟一条 filter pushdown

SQL：子查询或 aggregate 上 filter。用 EXPLAIN LOGICAL PLAN PROCESS，再停在 PlanTreeRewriteJob#rewrite；记录 pattern 命中和固定点。

练习 3 · 画出一个 Memo

SQL：两表 equi-join。断点：Memo#insertGroupExpression、ApplyRuleJob#execute。画出 Group、logical/physical expressions 与 rule masks。

练习 4 · 改变 Join 顺序

SQL：3–4 表 Join。切换统计或 reorder 开关，停在 Optimizer#isDpHyp 和 OptimizeGroupExpressionJob#getJoinRules，解释选了哪条 reorder 路径。

练习 5 · 追踪广播与 Shuffle

断点：RequestPropertyDeriver、CostModel#visitPhysicalHashJoin、CostAndEnforcerJob#recordPropertyAndCost。比较两组 child properties 与 scalar cost。

练习 6 · 人为制造未知统计

观察 StatsCalculator#computeOlapScan、disableJoinReorderIfStatsInvalid 与 Group stats reliability。先判断是否命中三类 invalid check；若只是 UNKNOWN，记录 left-zig-zag 选择和 DPHyp 阈值变化，不要预设重排已关闭。

练习 7 · 完成一次 HBO 双跑

使用 query_p0/hbo 的小型案例：第一次采集 Profile，第二次开启 optimization；停在 Profile#publishHboPlanStatistics 与 HboStatsCalculator 比较 delegate/history row count。

练习 8 · 从 PhysicalDistribute 到 Fragment

断点：chooseBestPlan、visitPhysicalDistribute、DistributePlanner#plan。区分 property enforcer、ExchangeNode、fragment instance。
