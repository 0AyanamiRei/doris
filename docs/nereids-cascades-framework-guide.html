01 · Architecture

从八个模块，归并为五个协作平面

CockroachDB 的八模块适合做功能清单；五平面更适合学习“责任边界”。映射是多对多的：例如 Properties 同时服务语义合法性和物理搜索，Search 同时操作 Memo 与 required property。

binding、类型、nullability、DataTrait、join/aggregate/window/CTE 语义，以及规则前置条件。

2

3

required/derived properties、implementation、child requirements、enforcer 与 best-plan table。

4

表/列统计、基数估计与 cost dimensions 共同驱动选择；通用模型常谈 CPU/I/O/network/memory，当前 Doris Cost 实装 CPU/memory/network。

02 · One query, many observations

实验主线：Q3 表上的简化三表查询

这不是标准 TPC-H Q3。它只复用 customer、orders、lineitem 三张表，去掉 aggregate 和 LIMIT，保留两次等值 join、三个单表 filter、四列 project 与 ORDER BY。这样第一次阅读时，每一层变化都有一个清晰来源。

SELECT
    c.c_custkey,
    o.o_orderkey,
    l.l_linenumber,
    o.o_orderdate
FROM customer c
JOIN orders o
  ON c.c_custkey = o.o_custkey
JOIN lineitem l
  ON o.o_orderkey = l.l_orderkey
WHERE c.c_mktsegment = 'BUILDING'
  AND o.o_orderdate < DATE '1995-03-15'
  AND l.l_shipdate > DATE '1995-03-15'
ORDER BY o.o_orderdate, o.o_orderkey, l.l_linenumber;

03 · How to read EXPLAIN

第一次看 EXPLAIN：八份结果分别在回答什么

不要把所有输出当成同一种“计划”。前三份是逻辑树的不同成熟度，PROCESS 是变化记录，Memo 是共享搜索空间，Shape/Physical 是赢家的两种视图，Distributed 才进入 fragment instance。下面每一节都链接本次完整原始结果。

先学会识别树上的符号

符号含义第一次阅读时怎么处理
+--、|-- 与缩进parent/child 结构；数据从叶子向根流动先从最底层 scan 向上读数据加工，再从根向下读 required order/distribution。
LogicalXxx / PhysicalXxx“算什么”与“怎样执行”LogicalJoin 不是已选择 Hash Join；看到 PhysicalHashJoin 才是 implementation 已确定。
[213]本次 plan node ID只用于在同一份输出中定位；重新执行会变化，不代表 cost 或执行顺序。
slot#12绑定后的 expression/slot identity同名列靠 ExprId 区分；不要把 #12 当列序号。
@13该 physical node 对应的 Memo Group ID用它从 PhysicalPlan 回查 Memo；ID 只在本次优化中有意义。
stats=48,443.3优化器估算的输出行数它是 cost 输入，不是运行时实际行数。
DistributionSpec*输出或要求的分布属性重点找 GATHER、REPLICATED、HASH 以及是谁插入 PhysicalDistribute。
Logical Expressions / Physical ExpressionsMemo 中的 logical/physical GroupExpression 条目不要理解成谓词、函数等标量 Expression；条目内部才持有一个 Plan operator。

04 · Intermediate representation

Plan 与 Expression：两套独立的泛型树，不是同一个概念

源码结论：Plan extends TreeNode<Plan>，Expression extends AbstractTreeNode<Expression>；后者间接实现 TreeNode<Expression>。二者共享 Nereids 的遍历协议，但 Plan 不是 Expression，Expression 也不是 Plan，更不存在“所有节点统一继承 Expression”的设计。
Nereids Plan treechildren(): List<Plan>
Filter / Join / Aggregate / Sort
持有
Plan#getExpressions()当前算子持有的谓词、投影、排序键、聚合函数
返回
Nereids Expression treechildren(): List<Expression>
EqualTo / And / Slot / Literal / Function

准确说法是：它们各自都能使用 TreeNode 的遍历/重写 API，但泛型 self type 把孩子限制在各自体系内。Plan tree 的边表示关系算子的输入；Expression tree 的边表示标量计算。Plan#getExpressions() 是“Plan 节点拥有标量表达式”的对象引用，不会把这些表达式变成 Plan#children()。例如 LogicalFilter 有一个 Plan child，同时持有 predicate expression tree。标量子查询是特殊交叉引用：SubqueryExpr 可持有一个 LogicalPlan，分析阶段再通过 Apply 等结构处理；这也没有改变两套泛型 children 的类型边界。

对象源码责任关键状态在简化查询中的例子
PlanNereids 所有逻辑/物理关系计划节点的统一接口；暴露 Plan children、owned scalar expressions、output、logical properties 和 memo 快速引用。PlanType、List<Plan> children、Optional<GroupExpression>Join、Filter、Project、Sort

05 · Transform language

Rule / RuleType：同一种外壳，三种核心用途

Rule 把“匹配什么、满足什么条件、产生什么计划”封装起来；RuleType 同时是唯一编号和类别标签。规则真正在哪个阶段运行，由 rule class、RuleSet 和 Job executor 共同决定。

Normalization / Rewrite

在 plan tree 上把表达式收敛到规范形，通常用新树替代旧树，不保留所有历史形态。例如 filter pushdown、project merge、nullable 调整。

Exploration

从一个 logical GroupExpression 产生逻辑等价表达式，并 copyIn(..., targetGroup, false) 到同一等价类。Join commute/associate/exchange 属于这里。

Implementation

把 logical operator 变成一个或多个 physical operator，以 physical GroupExpression 条目加入 Group，随后进入 property 与 cost 搜索。

一条 Rule 从声明到执行

  → OptimizeGroupExpressionJob 选择 exploration / implementation rules
  → ApplyRuleJob 用 GroupExpressionMatching 枚举匹配
  → rule.transform(matchedPlan, cascadesContext)

  → 新 logical GroupExpression：继续探索 + 派生统计

GroupExpression.ruleMasks 记录已应用的 RuleType，配合 disabled-rule bitset 和 root pattern 检查，避免在同一个表达式上无意义地重复执行同一规则。Memo 还会做结构去重，因此“规则被调用”不等于“搜索空间一定变大”。

为什么显式栈在 Group merge 和新 property 请求下仍能工作
  • GroupExpression.ruleMasks 防止同一 RuleType 在同一表达式上重复应用；Memo 的 canonical map 再过滤结构重复结果。
  • Group.isExplored 是 property-independent：新 required property 不会重跑全部 logical exploration，但仍会重新计价该 Group 已有 physical GroupExpressions。
  • Group.lowestCostPlans 才是 property-aware cache；只有 exact required property 已有 best 时 OptimizeGroupJob 才直接返回。
  • Group merge 后，栈中可能还有指向旧 GroupExpression 的 Job；isUnused 让这些陈旧 Job 安全退出。
  • statDerived 避免统计重复派生；scheduler 在每次 pop 前检查规划超时。
LIFO 的一个反直觉细节：OptimizeGroupExpressionJob 源码先 push exploration rules，后 push implementation rules，因此栈顶的 implementation jobs 会先执行。源码中的“push 顺序”不能直接当成“执行顺序”。

09 · Group × required property

物理属性、成本与 Enforcer：分布式搜索真正耦合的地方

PhysicalProperties 由 DistributionSpec + OrderSpec 组成。父节点的 required property 不是 Group 的固定字段，而是一次搜索请求；同一 Group 会按不同 property 保存不同 best plan。

术语校正：“每个 Group 的 required property”应更精确地写成“优化器曾对该 Group 发起的每个 required-property 请求”。Group.lowestCostPlans 的 key 集合就是已经求解的请求，而不是 Group 只有一个 property。

一次 physical GroupExpression 怎样被完整计价

  1. RequestPropertyDeriver 根据当前 physical operator 和父 required property，生成零个或多个“对子节点的属性要求元组”。
  2. 对元组中的每个 child，递归求 Best(childGroup, requestedChildProperty)；若尚未求出，用 continuation 暂停父 job。
  3. ChildrenPropertiesRegulator 校正可行的孩子输出组合，ChildOutputPropertyDeriver 再推导当前算子的 output property。
  4. CostCalculator 计算节点 cost 并累加 child costs；记录 GroupExpression 的 lowest-cost table 和 Group 的 Best(G, P)。
  5. 若 output 不满足父 required，EnforceMissingPropertiesHelper 添加 sort/distribution enforcer，重新计价并参与同一 best-plan 比较。

  LOCAL_SORT(child requires ANY)

one phase:

Required、child request、derived output 与 enforcer 的关系

当前 Doris Enforcer 的实际边界

  • distribution 不满足：DistributionSpec.addEnforcer() 构造 PhysicalDistribute<GroupPlan>。
  • order 不满足：OrderSpec 构造 local 或 global PhysicalQuickSort。
  • order 与 distribution 同时不满足时，helper 按 GATHER、must-local-sort 等情况决定 sort/distribute 顺序，因为 redistribution 可能破坏已有顺序。
  • 当前这条通用 enforcement 路径没有 generic spool/materialize enforcer；不能把其他 Cascades 系统的 enforcer 清单直接当作 Doris 现状。

统计与 cost 怎样接进来

DeriveStatsJob 自底向上为 GroupExpression 调用 StatsCalculator；启用 HBO 时改用 HboStatsCalculator。Cost 保存 CPU、memory、network 三个分量，并按 session cost weights 折算成一个 scalar value；CostCalculator.addChildCost 把节点和子树分量相加。

不要套用通用清单：当前 Cost 没有独立的 sequential/random I/O 字段，也没有单独的 spill 字段。相关影响只能体现在具体算子公式、统计量、系数或未来模型演进中。文档讲“估计平面”时应区分理想维度与当前代码。

源码逐步展开

  1. Optimizer.execute() 先对 normalized plan 调用 CascadesContext.toMemo()，并对 root logical GroupExpressions 运行 DeriveStatsJob。这是 Memo #1。
  2. Optimizer.isDpHyp() 比较的是 Memo.countMaxContinuousJoin(rewritePlan) 得到的“最大连续 LogicalJoin 算子数”，不是表数。自动选择条件是 continuousJoinNum > maxTableCountUseCascadesJoinReorder；默认阈值为 10，列统计未知时翻倍。普通连通的 N 表二叉 join 通常有 N−1 个 join 算子，因此已知统计下默认从 12 表起才可能自动选择 DPHyp。本三表教学查询需显式设置 enable_dphyp_optimizer=true。
  3. JoinOrderJob 找到可重排 join cluster，HyperGraph.Builder 将非 join 子树变成 nodes、join predicate 变成 edges；SubgraphEnumerator 按 CSG/CMP 枚举合法连接。
  4. PlanReceiver 的 DP table 是 bitmap → Group。每次 emit 用左右 subset Group 的 GroupPlan 构造 LogicalJoin / LogicalProject，为新 subset 建 Group，并调用 Memo.copyIn()。
  5. 新 join GroupExpression 立即通过 OptimizeGroupExpressionJob(..., ANY) 产生物理实现、child property 组合和 cost；因此 DPHyp 的 DP 决策已经借用了 Cascades 的 implementation/property/cost 基础设施，但此时求解目标是 ANY。
  6. 枚举结束后，MemoStatsAndCostRecomputer.recompute(root, ANY, ...) 重新估计临时 Memo 的 logical row count 与 physical costs，再由 copyOutBestLogicalPlan() 抽出最低成本 logical tree。
  7. 选中树在临时 CascadesContext 中运行 hash-condition pushdown、column pruning、project merge、nullable 调整与校验；主 context 随后 releaseMemo()，把这棵树设为 rewrite plan，并再次 toMemo()。这是 Memo #2。
  8. 最终统一执行 OptimizeGroupJob(root, GATHER)。after-DPHyp rule set、implementation rules、stats、required/derived properties、enforcers，以及针对已选 logical tree 的最终 property/cost search 在新 Memo 上完成。
最重要的观察结论：EXPLAIN MEMO PLAN 展示的是重建后的最终 Memo，不是保留了全部 DPHyp subset/join-tree alternatives 的 Memo #1。若要研究 CSG/CMP 枚举，必须同时看 enable_dphyp_trace 日志或在 PlanReceiver#emitCsgCmp 下断点。

读 Cascades 源码最常见的十五个误区

误区当前 Doris 源码中的准确说法
Nereids Plan 与 Expression 是同一种节点它们分别使用 TreeNode<Plan> 与 TreeNode<Expression>，只共享遍历协议；children 类型、语义和 visitor 都彼此独立。
Expression 就是 GroupExpression前者是标量树；后者是 Memo 中“plan operator + child Groups”的关系表达式。
看到 planner.PlanNode 就说明走了旧优化器当前普通 query 只构造 NereidsPlanner；最优 Nereids PhysicalPlan 仍会翻译成既有 PlanNode/Expr/PlanFragment 供执行层使用。
输出 Schema 一样就能进入同一 GroupSchema/nullability 只是必要检查；等价性必须由合法 transformation 保证，Memo 不做语义证明。
一个 Group 只有一个 logical GroupExpression初始化时通常一个；exploration 后可以有多个。getLogicalExpression() 只适用于代码明确保证唯一的上下文。
一个 Group 有一个全局 best planbest table 的 key 是 required PhysicalProperties；正确写法是 Best(G, P)。
required property 是 Group 固有属性它随 JobContext 请求向下传播；Group 只是缓存已经求解的 property entries。
每个 join 都会同时比较 Hash / Merge / NLJHash 与 NLJ implementation rule 由 shouldNestedLoopJoin 互斥；当前没有 Physical Merge Join。
Broadcast Join、Shuffle Join 是不同 physical join 节点它们通常是同一个 PhysicalHashJoin 的不同 child-property 方案，必要时由 PhysicalDistribute 补齐。
所有 Rewrite 都在 JobStack 上按 LIFO 排队Rewriter 外层按 batch list 执行；深树 traversal 才进入显式 JobStack。CBO jobs 则由 SimpleJobScheduler 串行 drain。
RulePromise 决定当前实际执行顺序虽然枚举描述 promise priority，当前 SimpleJobScheduler / OptimizeGroupExpressionJob 不按 promise 排序；实际顺序由 rule list 的 push 顺序和 LIFO 决定。
DPHyp alternatives 都保留在最终 Memo当前实现从 Memo #1 copy-out 最佳 logical tree，rewrite 后释放并重建 Memo #2；最终 Memo 不保留完整 DP table。
DPHyp join order 与 root GATHER/Sort 完全联合搜索Memo #1 在 ANY 下先选一棵 logical tree；Memo #2 才优化最终 GATHER、Sort 和 enforcer。后者不能重新选回已被 Memo #1 丢弃的 join order。
PhysicalDistribute 就是运行时 Exchange instance它是 CBO enforcer；translator 再生成 ExchangeNode / fragments；DistributePlanner 最后分配 worker instances。
cost 就是预估执行时间当前是 CPU/memory/network 分量的加权比较标尺，用于候选排序；不是毫秒预测，也没有独立 I/O/spill 分量。
